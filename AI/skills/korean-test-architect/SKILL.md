# Korean Test Architect

이 스킬은 테스트 코드를 단순한 코드 검증 도구가 아닌, 타인이 읽었을 때 시스템의 기능을 한눈에 파악할 수 있는 **'살아있는 명세서(Living Documentation)'**로 만드는 데 목적이 있습니다.

## 📋 핵심 원칙

1. **목적**: 
    - 시스템의 정상 동작을 엄격하게 검증한다.
    - 타인이 읽었을 때 구현된 기능의 요구사항과 동작 방식이 명확히 전달되는 명세서 역할을 수행한다.

2. **구조적 설계 (The Hierarchy)**:
    - **GIVEN**: 테스트를 위한 구체적인 상황 설정. `describe`로 감싼다.
    - **WHEN**: 검증하려는 핵심 행위(Action). `describe`로 감싼다.
    - **THEN**: 기대하는 결과와 검증. `it`으로 감싼다.
    - **1-it-1-expect**: 하나의 `it` 블록에서는 단 하나의 명확한 사실만 검증한다.

3. **언어 및 표현**:
    - GIVEN, WHEN, THEN의 설명은 반드시 **한글**로 작성한다.
    - 예시: `GIVEN: 특정 가격과 날짜를 가진 숙소가 3개 등록된 상황에서`, `WHEN: 사용자가 최저가순으로 검색을 수행한다면`, `THEN: 첫 번째 결과의 가격은 모든 숙소 중 가장 낮아야 한다`.

4. **검증 범위 (Branch Points)**:
    - 성공 케이스뿐만 아니라, 의미 있는 비정상 동작(에러 케이스, 경계값 등)도 포함한다.
    - 기계적인 모든 분기점 나열이 아닌, **도메인 관점에서 가치 있는 케이스**를 선별하여 설계한다. (양보다 질)

## 🛠 작성 가이드

### 테스트 코드 템플릿 (Jest/NestJS 예시)

```typescript
describe('기능 명칭 (예: 숙소 검색)', () => {
  describe('GIVEN: [구체적인 상황 설명]', () => {
    // BeforeAll/Each 등을 이용한 데이터 셋업
    
    describe('WHEN: [핵심 행동 실행]', () => {
      // 실제 대상 메서드 호출
      
      it('THEN: [기대하는 결과 1]', async () => {
        expect(...).toBe(...);
      });

      it('THEN: [기대하는 결과 2]', async () => {
        expect(...).toBe(...);
      });
    });
  });
});
```

### 주의 사항
- `...`와 같은 생략 기호를 사용하지 않고 전체 코드를 작성한다.
- 테스트 데이터는 하드코딩보다 명확한 변수명을 사용하여 의도를 드러낸다.
