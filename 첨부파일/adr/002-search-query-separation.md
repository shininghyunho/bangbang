# [ADR-002] 프론트엔드 UI/UX 요구사항에 맞춘 검색 쿼리 분리 및 Over-fetching 방지 전략

## 1. Summary
- **결정**: 예약 가능한 숙소 목록과 날짜별 상세 요금을 한 번에 조회하는 복잡한 단일 쿼리(1방 쿼리)를 지양하고, 목록 조회 쿼리(총합)와 상세 요금 조회 쿼리(개별 일자)로 책임을 분리함.
- **날짜**: 2026-04-29

## 2. Context (배경)
- **문제 상황**: 
  - 초기 설계에서는 숙소 검색 시 해당 숙소의 기본 정보(이름, 주소 등)와 검색된 날짜(예: 3일간)별 상세 가격 정보를 한 번의 조인 쿼리로 모두 가져오려 했음. 
  - 이로 인해 숙소 1개당 날짜 수만큼 데이터 행(Row)이 복제되어(Cartesian Product) 반환되는 심각한 네트워크 대역폭 낭비(Over-fetching)가 발생하였음.
  - 또한 쿼리 구조가 지나치게 복잡해져 유지보수성이 저하됨.
- **요구 사항 및 제약**: 실제 프론트엔드 검색 결과 화면(List View)에서는 숙소별 '총 가격'만 노출되며, '일자별 상세 가격'은 사용자가 특정 숙소를 클릭하여 모달(Modal) 창을 열었을 때만 필요함.

## 3. Alternatives (대안 목록)
- **대안 A**: 복잡한 조인 및 서브쿼리를 활용한 단일(1방) 쿼리 (모든 정보 일괄 응답)
  - DB와 애플리케이션 간 통신 횟수는 1번으로 최소화됨.
  - 검색 결과 데이터가 기하급수적으로 커지며, 프론트엔드에서 데이터를 재가공(Grouping)해야 하는 부담 발생.
- **대안 B (선택)**: 검색 목록 조회(총 요금 계산) 쿼리와 상세 요금 조회(일자별) 쿼리의 분리
  - UI 렌더링 시점에 맞춰 필요한 데이터만 지연 로딩(Lazy Loading) 방식으로 제공.
  - 각각의 쿼리가 단순해져 가독성과 유지보수성이 크게 향상됨.

| 비교 항목 | 대안 A (단일 쿼리 일괄 응답) | 대안 B (목록/상세 분리 응답 - 선택) |
| :--- | :--- | :--- |
| **데이터 중복도** | 매우 높음 (숙소 정보 * 날짜 수) | **없음 (최적화된 크기)** |
| **쿼리 복잡성** | 높음 (Window Function, 다중 JOIN) | **낮음 (단순 JOIN 및 GROUP BY)** |
| **UI 최적화** | 낮음 (불필요한 상세 데이터 선별 필요) | **높음 (화면 전환에 맞춘 온디맨드 로딩)** |

## 4. Decision (결정)
- **결론**: **대안 B (쿼리 및 API 엔드포인트 분리) 도입**
- **근거**: 검색 성능 측면에서 두 방식 모두 복합 인덱스(`idx_covering_search`)를 적절히 타기 때문에 속도 차이는 미미함. 그러나 유지보수성과 네트워크 페이로드 크기를 고려할 때 쿼리를 분리하는 것이 훨씬 이점이 큼. 특히 검색 결과는 100개로 제한(`LIMIT 100`)되므로 분리된 쿼리 구조가 시스템 부하를 일으키지 않음.

## 5. Trade-offs (Pros/Cons)
- **Pros (얻은 것)**
  - **Over-fetching 해결**: 불필요한 일자별 상세 데이터를 초기에 로드하지 않아 API 응답 페이로드가 극적으로 감소함.
  - **유지보수성 향상**: 쿼리가 `GROUP BY`와 `HAVING COUNT` 수준의 직관적인 구조로 단순화되어 수정 및 디버깅이 용이해짐.
  - **프론트엔드 부하 감소**: 프론트엔드에서 중복된 행 데이터를 파싱하고 묶어주는 복잡한 로직이 제거됨.
- **Cons (포기한 것)**
  - **API 호출 횟수 증가 (잠재적)**: 상세 정보를 보기 위해 추가적인 API 호출(네트워크 I/O)이 발생함.

## 6. Retrospective (회고)
- **성과**: 쿼리를 분리하면 일반적으로 'N+1 문제'가 발생할 것이라 우려했으나, 실제 UI 흐름상 검색 목록에서는 '가격 총합'만 보여주고, 상세 요금은 사용자가 '특정 숙소를 클릭했을 때 단 1번만' 요청하므로 N+1 이슈가 발생하지 않음을 증명함.
- **한계 및 배운 점**: 기능 구현 시 백엔드의 '1방 쿼리' 강박에서 벗어나야 함을 배웠음. 데이터베이스 관점의 최적화만큼이나 프론트엔드에서 어떤 단위(컴포넌트)로 데이터가 소비되는지를 이해하고 API 크기를 설계하는 것이 진정한 시스템 최적화이자 풀스택 관점의 아키텍처 설계임을 깊이 체감함.
