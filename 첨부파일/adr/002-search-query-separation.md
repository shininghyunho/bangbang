# [ADR-002] 검색 쿼리 분리 전략

## 1. Summary
- 결정: 예약 가능한 숙소 목록과 날짜별 상세 요금을 한 번에 조회하는 단일 쿼리를 지양하고, 목록 조회 쿼리(총합)와 상세 요금 조회 쿼리(개별 일자)로 책임을 분리함.
- 날짜: 2026-04-29

## 2. Context (배경)
- 문제 상황: 
  - 초기 설계에서는 숙소 검색 시 해당 숙소의 기본 정보(이름, 주소 등)와 검색된 날짜(예: 3일간)별 상세 가격 정보를 한 번의 조인 쿼리로 모두 가져오려 했음. 
  - 이로 인해 숙소 1개당 날짜 수만큼 데이터 행(Row)이 복제되어(Cartesian Product) 반환되는 Over-fetching이 발생.
  - 쿼리 구조가 복잡해져(Window Function, 다중 JOIN) 유지보수성이 저하됨.
- 요구 사항 및 제약: 실제 프론트엔드 검색 결과 화면(List View)에서는 숙소별 '총 가격'만 노출되며, '일자별 상세 가격'은 사용자가 특정 숙소를 클릭하여 모달(Modal) 창을 열었을 때만 필요함.

## 3. Alternatives (대안 목록)
- 대안 A: 단일 쿼리로 모든 정보를 일괄 응답
  - DB와 애플리케이션 간 통신 횟수는 1번으로 최소화됨.
  - 검색 결과 데이터가 기하급수적으로 커지며, 프론트엔드에서 데이터를 재가공(Grouping)해야 하는 부담 발생.
- 대안 B (선택): 검색 목록 조회(총 요금 계산)와 상세 요금 조회(일자별)를 분리
  - UI 렌더링 시점에 맞춰 필요한 데이터만 지연 로딩(Lazy Loading) 방식으로 제공.
  - 각각의 쿼리가 단순해져 가독성과 유지보수성이 향상됨.

| 비교 항목 | 대안 A (단일 쿼리 일괄 응답) | 대안 B (목록/상세 분리 응답 - 선택) |
| :--- | :--- | :--- |
| 데이터 중복도 | 매우 높음 (숙소 정보 × 날짜 수) | 없음 (필요한 크기만 응답) |
| 쿼리 복잡성 | 높음 (Window Function, 다중 JOIN) | 낮음 (단순 JOIN 및 GROUP BY) |
| UI 최적화 | 낮음 (불필요한 상세 데이터 선별 필요) | 높음 (화면 전환에 맞춘 온디맨드 로딩) |

## 4. Decision (결정)
- 결론: 쿼리 및 API 엔드포인트 분리 도입
- 근거: 검색 성능 측면에서 두 방식 모두 복합 인덱스(`idx_covering_search`)를 타기 때문에 속도 차이는 미미함. 그러나 유지보수성과 네트워크 페이로드 크기를 고려할 때 쿼리를 분리하는 것이 이점이 큼. 검색 결과는 최대 100개로 제한(`LIMIT 100`)되므로 분리된 쿼리 구조가 시스템 부하를 일으키지 않음.

## 5. Trade-offs (Pros/Cons)
- Pros (얻은 것)
  - Over-fetching 해결: 불필요한 일자별 상세 데이터를 초기에 로드하지 않아 API 응답 페이로드가 크게 감소함.
  - 유지보수성 향상: 쿼리가 `GROUP BY`와 `HAVING COUNT` 수준의 직관적인 구조로 단순화됨. Service 레이어에서 쿼리 결과를 후처리하던 로직도 제거됨.
  - 프론트엔드 부하 감소: 프론트엔드에서 중복된 행 데이터를 파싱하고 묶어주는 복잡한 로직이 제거됨.
- Cons (포기한 것)
  - API 호출 횟수 증가: 상세 정보를 보기 위해 추가적인 API 호출이 발생함. 단, 사용자의 클릭 액션이 있을 때만 1회 호출되므로 N+1 문제와는 다름.

## 6. Retrospective (회고)

처음에는 N+1 문제를 의식하며, 한 화면에 필요한 모든 정보를 한 번의 쿼리로 가져오려 했다. 그랬더니 SQL에 Window Function과 다중 JOIN이 들어가며 쿼리가 복잡해졌고, Service 단에서도 쿼리 결과를 프론트에 맞게 후처리해야 하는 로직이 생겼다.

다시 생각해보니, 메인 검색 화면에서 실제로 필요한 건 숙소별 '총 가격'뿐이었다. 일자별 상세 가격은 사용자가 특정 숙소를 클릭했을 때만 필요하므로, 굳이 모든 데이터를 한 번에 가져올 이유가 없었다. 쿼리를 목록 조회와 상세 조회로 나누자 SQL도 간결해졌고, Service 레이어의 후처리 로직도 사라져 코드 전체가 깔끔해졌다.

쿼리를 나눠도 두 쿼리 모두 인덱스를 타기 때문에 성능상 문제는 없었고, 오히려 불필요한 데이터를 가져오지 않으니 메모리도 절약되었다.

이 판단을 할 수 있었던 건, 직접 React로 프론트엔드를 구현한 경험이 컸다. 이전에 백엔드만 개발할 때는 프론트가 필요로 하는 데이터를 한 번에 다 넘기는 것이 당연하다고 생각했다. 그러나 직접 화면을 만들어보니 어떤 시점에 어떤 데이터가 필요한지가 보였고, 그에 맞춰 API를 설계하는 것이 백엔드와 프론트엔드 모두에게 이점이 있음을 알게 되었다.
