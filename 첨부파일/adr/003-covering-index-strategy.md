# [ADR-003] Random I/O 제거를 위한 복합 커버링 인덱스(Covering Index) 설계

## 1. Summary
- **결정**: 400만 건의 `listing_schedule` 테이블에서 발생하는 심각한 디스크 I/O 병목을 해결하기 위해, 해당 테이블의 조회 조건과 조인 키만을 포함하는 타겟 커버링 인덱스 `idx_covering_search(isAvailable, date, price, listingId)`를 도입함.
- **날짜**: 2026-04-29

## 2. Context (배경)
- **문제 상황**: 기간(`date`), 가격(`price`), 가용성(`isAvailable`)을 필터링하는 검색 쿼리가 평균 9,000ms 이상 소요됨. 일반적인 Secondary Index를 태우더라도, 인덱스 탐색 후 실제 데이터를 가져오기 위해 Clustered Index(PK)를 다시 찾아가는 과정에서 대량의 디스크 Random I/O가 발생함.
- **요구 사항 및 제약**: 실시간 서비스에 적합한 10ms 이내의 응답 속도를 보장해야 함. 단, 무분별하게 모든 컬럼을 인덱스로 만들면 `INSERT` 성능이 극단적으로 저하되므로, 데이터 개수가 적은 `listings` 테이블의 조건(`guestCapacity` 등)은 인덱스에서 제외하고 병목의 핵심인 `listing_schedule` 테이블만 타겟팅해야 함.

## 3. Alternatives (대안 목록)
- **대안 A**: 일반적인 필터링 용도의 복합 인덱스 (예: `(isAvailable, date, price)`)
  - 인덱스 크기가 작아 쓰기(Insert) 성능 저하가 적음.
  - 필터링 후 `listingId`를 읽어오기 위해 원본 테이블에 접근해야 하므로 Random I/O 발생.
- **대안 B (선택)**: 조인 키까지 포함한 타겟 커버링 인덱스 `(isAvailable, date, price, listingId)`
  - `listing_schedule`에 대한 쿼리 처리가 인덱스 리프 노드에서 완결되어 Random I/O 원천 차단.
  - 인덱스 크기 증가로 인한 쓰기 부하 증가 우려.

| 비교 항목 | 대안 A (일반 복합 인덱스) | 대안 B (커버링 인덱스 - 선택) |
| :--- | :--- | :--- |
| **B-Tree 탐색 횟수** | 2회 (Secondary + Clustered) | **1회 (Secondary 단독)** |
| **디스크 I/O 패턴** | Random I/O 발생 | **Sequential I/O (인덱스 스캔)** |
| **Buffer Pool 효율** | 레코드 전체 캐싱 필요 | **인덱스 페이지만 캐싱 (고효율)** |

## 4. Decision (결정)
- **결론**: **대안 B (커버링 인덱스 전략 - C7) 채택**
- **근거**: 무작정 인덱스를 넓게 잡은 것이 아니라, MySQL B-Tree 구조에 대한 이해를 바탕으로 **조회(Query)와 쓰기(Insert) 성능을 교차 검증**하여 내린 결정임. 
  - **연산자 우선의 법칙**: 일반적으로 카디널리티(값의 종류)가 높은 컬럼을 인덱스 선두에 두는 것이 정석으로 알려져 있음. 그러나 본 실험을 통해 카디널리티가 단 2개뿐인 `isAvailable` 컬럼이라 하더라도, **등치 연산(`=`)으로 사용될 경우 범위 연산(`BETWEEN`)인 `date`나 `price`보다 인덱스 선두에 위치해야 B-Tree의 수직적 탐색(Seeking)이 가능함**을 증명함.
  - **쓰기 성능 검증**: 커버링 인덱스(C7)는 보조 인덱스가 없는 베이스라인(C0) 대비 `INSERT` 속도 저하가 약 5%(0.53ms)에 불과한 반면, 쿼리 스캔 행수(`Rows`)를 압도적으로 최적화함.

### 📊 통합 실험 벤치마크 결과 (후보군 C0~C7 전체)
| 후보군 | 인덱스 구성 컬럼 | Query (ms) | Insert (ms) | Rows (Scan) | 비고 (실행 계획) |
| :--- | :--- | :---: | :---: | :---: | :--- |
| **C0** | (None / Baseline) | 2,485.0 | **10.08** | 4,020,000 | 풀 스캔 (최악) |
| **C1** | `(date)` | 14.5 | 10.15 | 3,000 | 단일 범위 필터링 |
| **C2** | `(price)` | 2,485.0 | 10.12 | 4,020,000 | Table scan (Optimizer Skip) |
| **C3** | `(date, price)` | 7.72 | 10.14 | 2,249 | `isAvailable` 누락 시 성능 |
| **C4** | **`(isAvailable, date, price)`** | 7.89 | 10.27 | **2,017** | **등치 선두 (Seeking 성공)** |
| **C5** | `(date, isAvailable, price)` | 11.2 | 10.30 | 2,224 | 범위 선두 (Index Skip 발생) |
| **C6** | `(date, price, isAvailable)` | 9.43 | 10.07 | 2,249 | 범위 선두 (Filtering 전락) |
| **C7** | **`(isAvail, date, price, listingId)`** | **5.91** | 10.61 | **2,017** | **Covering Index (최종 선택)** |

## 5. Trade-offs (Pros/Cons)
- **Pros (얻은 것)**
  - **Random I/O 제거**: `Using index` 달성으로 조회 성능 900배 향상 (9,000ms -> 5ms 내외).
  - **선택적 최적화**: 레코드 수가 적은 `listings` 테이블을 배제하고, 400만 건의 `listing_schedule`만 커버링하여 불필요한 인덱스 비대화를 방지함.
- **Cons (포기한 것)**
  - **미세한 쓰기 지연**: 베이스라인(10.08ms) 대비 커버링 인덱스(10.61ms) 적용 시 `INSERT` 성능이 소폭 하락함. 단, 이는 시스템에서 충분히 수용 가능한 임계치 내의 트레이드오프임.

## 6. Retrospective (회고)
- **성과 (공학적 패러다임 전환)**
  - **카디널리티의 함정 극복**: "카디널리티가 높은 컬럼을 인덱스 앞에 두라"는 단편적인 정석에서 벗어나, B-Tree의 물리적 탐색 구조에서는 **연산자의 종류(등치 `=` vs 범위 `BETWEEN`)가 탐색(Seeking)과 스캔(Scan)을 가르는 결정적 요인**임을 실험으로 증명함.
  - **Trade-off에 기반한 의사결정**: "인덱스를 걸면 무조건 좋다"가 아니라, 쿼리 응답 속도 향상이라는 이득(수천 배)이 `INSERT` 성능 저하라는 비용(약 5%)을 압도적으로 상회한다는 정량적 데이터를 근거로 커버링 인덱스의 당위성을 확보함.
- **한계 및 보완 (검색 아키텍처의 한계 인식과 분산 설계)**
  - **RDBMS 다중 조건 검색의 한계**: 본 프로젝트는 RDBMS 내에서 검색 성능을 극한으로 끌어올리는 학습을 목적으로 커버링 인덱스를 적용함. 그러나 향후 편의시설, 지역, 평점 등 다양한 필터 조건이 추가될 경우, MySQL의 복합 인덱스만으로 대응하는 것은 인덱스 비대화 및 쓰기 성능 저하를 초래하여 시스템 구조를 경직되게 만듦.
  - **차세대 아키텍처 설계 (ES + Redis)**: 대용량 다중 조건 검색의 근본적 해결을 위해서는 저장소의 역할 분리가 필수적임을 깨달음. 향후 상용 수준의 아키텍처로 고도화한다면 다음의 3-Tier 구조를 도입할 것임.
    1. **후보군 추출 (Elasticsearch)**: 역인덱스(Inverted Index)를 활용하여 복잡한 다중 조건(지역, 가격, 시설 등 정적 데이터)에 맞는 숙소 후보군을 빠르게 1차 필터링함.
    2. **가용성 검증 (Redis)**: 초당 수만 번씩 변경될 수 있는 '날짜별 예약 가능 여부(동적 데이터)'를 인메모리 캐시에서 초고속으로 2차 필터링함.
    3. **진실의 원천 (MySQL)**: 검색의 책임을 ES와 Redis에 위임하고, MySQL은 본연의 역할인 '최종 예약 확정 시의 트랜잭션 무결성(ACID) 보장'에만 집중함.
