# [ADR-003] 실험 기반의 복합 인덱스 설계

## 1. Summary
- 결정: 약 300만 건의 `listing_schedule` 테이블에서 발생하는 검색 성능 문제를 해결하기 위해, 8가지 인덱스 후보군을 구성하여 Read/Write/실행 계획을 비교 실험한 뒤 커버링 인덱스 `idx_covering_search(isAvailable, date, price, listingId)`를 도입함.
- 날짜: 2026-04-29

## 2. Context (배경)
- 문제 상황: 기간(`date`), 가격(`price`), 가용성(`isAvailable`)을 필터링하는 검색 쿼리가 평균 9,000ms 이상 소요됨. 인덱스 없이 약 300만 건의 테이블을 풀 스캔하고 있었음.
- 요구 사항 및 제약: 검색 응답 속도를 10ms 이내로 줄여야 함. 단, 인덱스를 무분별하게 추가하면 `INSERT` 성능이 저하되므로, 숙소 예약 서비스의 Read/Write 비율을 고려하여 인덱스 설계를 진행해야 함.

## 3. Alternatives (대안 목록)
- 대안 A: 일반적인 필터링 용도의 복합 인덱스 (예: `(isAvailable, date, price)`)
  - 인덱스 크기가 작아 Insert 성능 저하가 적음.
  - 필터링 후 `listingId`를 읽어오기 위해 원본 테이블에 접근해야 하므로 Random I/O 발생.
- 대안 B (선택): 조인 키까지 포함한 커버링 인덱스 `(isAvailable, date, price, listingId)`
  - 쿼리에 필요한 모든 컬럼이 인덱스에 포함되므로 원본 테이블 접근 없이 인덱스만으로 조회가 완결됨.
  - 인덱스 크기 증가로 인한 쓰기 부하 증가 우려.

| 비교 항목 | 대안 A (일반 복합 인덱스) | 대안 B (커버링 인덱스 - 선택) |
| :--- | :--- | :--- |
| 테이블 접근 | 인덱스 탐색 후 원본 테이블 접근 필요 | 인덱스만으로 조회 완결 |
| 디스크 I/O | Random I/O 발생 | 인덱스 스캔만 발생 |
| Insert 영향 | 상대적으로 적음 | 인덱스 크기 증가로 소폭 저하 |

## 4. Decision (결정)
- 결론: 커버링 인덱스(C7) 채택
- 근거: 단순히 "커버링 인덱스가 좋다"는 이론에 따른 것이 아니라, 아래와 같은 질문들을 하나씩 실험으로 검증하며 도출한 결정임.
  - 인덱스가 꼭 필요한가? → C0(인덱스 없음)과 비교하여 풀 스캔의 비용을 확인함.
  - 어떤 컬럼을 인덱스에 넣어야 하는가? → C1~C3에서 단일/2개 컬럼 조합의 효과를 측정함.
  - 컬럼 순서가 중요한가? → C4, C5, C6에서 동일한 컬럼 조합의 순서만 바꿔가며 실행 계획을 비교함. 카디널리티가 낮은 `isAvailable`이라도 등치 조건(`=`)으로 사용되면 선두에 위치해야 인덱스를 효율적으로 탈 수 있었음.
  - 인덱스를 넓히면 Insert에는 문제가 없는가? → 모든 후보군에 대해 Insert 속도를 함께 측정하여, C7의 Insert 저하가 약 5%(0.53ms)로 수용 가능한 수준임을 확인함.

### 벤치마크 결과 (후보군 C0~C7)
| 후보군 | 인덱스 구성 컬럼 | Query (ms) | Insert (ms) | Rows (Scan) | 비고 (실행 계획) |
| :--- | :--- | :---: | :---: | :---: | :--- |
| C0 | (None / Baseline) | 2,485.0 | 10.08 | 4,020,000 | 풀 스캔 |
| C1 | `(date)` | 14.5 | 10.15 | 3,000 | 단일 범위 필터링 |
| C2 | `(price)` | 2,485.0 | 10.12 | 4,020,000 | Optimizer가 인덱스 무시 |
| C3 | `(date, price)` | 7.72 | 10.14 | 2,249 | `isAvailable` 누락 시 |
| C4 | `(isAvailable, date, price)` | 7.89 | 10.27 | 2,017 | 등치 조건 선두 배치 |
| C5 | `(date, isAvailable, price)` | 11.2 | 10.30 | 2,224 | 범위 조건 선두 배치 |
| C6 | `(date, price, isAvailable)` | 9.43 | 10.07 | 2,249 | 범위 조건 선두 배치 |
| C7 | `(isAvail, date, price, listingId)` | 5.91 | 10.61 | 2,017 | Covering Index (최종 선택) |

## 5. Trade-offs (Pros/Cons)
- Pros (얻은 것)
  - 조회 성능 개선: 인덱스 없는 상태(9,000ms+)에서 약 5ms 수준으로 개선됨.
  - 선택적 최적화: 레코드 수가 적은 `listings` 테이블을 배제하고, 약 300만 건의 `listing_schedule`만 대상으로 인덱스를 설계하여 불필요한 인덱스 비대화를 방지함.
- Cons (포기한 것)
  - Insert 성능 소폭 하락: 베이스라인(10.08ms) 대비 커버링 인덱스(10.61ms) 적용 시 Insert 속도가 약 5% 하락함. 단, Airbnb와 같은 숙소 검색 플랫폼은 검색(Read)이 예약 등록(Write)보다 압도적으로 많으므로 수용 가능한 수준으로 판단함.

## 6. Retrospective (회고)

이 작업에서 가장 값진 경험은 추론에 그치지 않고 철저히 실험 데이터에 따른 의사결정을 했다는 것이다.

처음에는 "인덱스를 걸면 빨라진다"는 막연한 이해만 있었다. 그래서 Real MySQL 도서와 MySQL 공식 문서를 읽으며 인덱스의 동작 원리를 학습한 뒤, 실제로 여러 의문점을 실험으로 하나씩 확인해 나갔다.

- 인덱스가 없으면 실제로 얼마나 느린가? (C0)
- 어떤 컬럼 조합이 효과적인가? (C1~C3)
- 같은 컬럼이라도 순서를 바꾸면 실행 계획이 달라지는가? (C4 vs C5 vs C6)
- 인덱스에 컬럼을 하나 더 추가하면 Insert에는 얼마나 영향을 주는가? (C7)
- 이렇게 만든 인덱스가 다른 쿼리(상세 요금 조회 등)에서도 활용될 수 있는가?

이 과정을 통해 "카디널리티가 높은 컬럼을 앞에 두라"는 일반적인 규칙이 항상 맞는 것은 아니라는 점, 인덱스는 Read 성능만이 아니라 Write 성능과의 균형 속에서 판단해야 한다는 점을 직접 데이터로 확인할 수 있었다.

기술적인 측면에서는, 현재 프로젝트의 검색 조건(날짜, 가격, 가용성)에는 MySQL 복합 인덱스로 충분히 대응할 수 있었다. 다만 향후 지역, 편의시설, 평점 등 필터 조건이 늘어난다면 복합 인덱스만으로는 한계가 있을 것이라는 점은 인지하고 있다.
